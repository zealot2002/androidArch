## 第一篇：主流Android架构十年演化史：我们到底在解决什么问题？

### 前言
从2010年Android诞生至今，Android架构经历了至少五次大规模的迭代。从最初的MVC到现在的MVI，每一次架构革命都伴随着无数开发者的争论、踩坑和重构。我们学习了MVC的分层思想，掌握了MVP的解耦技巧，拥抱了MVVM的数据绑定，推崇Clean Architecture的依赖倒置，现在又开始追捧MVI的单向数据流。

但一个扎心的问题是：当我们把这些架构都学会、都用遍之后，我们的代码就真的变好了吗？

### 一、架构演化的本质：减少连线，降低复杂度
让我们用一个最简单的模型来理解所有架构的演化：**连线数越少，复杂度越低**。

#### 1. MVC：最初的分层尝试（6根连线）
MVC是所有架构的鼻祖，它将代码分为三层：
- Model：数据层
- View：视图层
- Controller：控制层

MVC的问题在于**三者两两交互**，形成了一个三角形的依赖关系。View可以直接访问Model，Model变化也可以直接通知View，Controller同时依赖两者。这就导致了6根连线的复杂关系：
- View → Controller
- View → Model
- Controller → View
- Controller → Model
- Model → View
- Model → Controller

在Android中，Activity同时承担了View和Controller的职责，最终演变成了"Massive View Controller"，几千行的Activity成为常态。

#### 2. MVP：切断View与Model的直接联系（4根连线）
MVP是对MVC的第一次重大改进，它做了一个最简单但最有效的改变：**禁止View和Model直接交互**。

所有的交互都必须通过Presenter进行：
View ←→ Presenter ←→ Model

连线数从6根减少到了4根，复杂度直接降低了33%。View只负责展示，Model只负责数据，Presenter负责业务逻辑。这在当时极大地改善了代码的可维护性。

但MVP也带来了新的问题：View和Presenter之间的接口爆炸，以及大量的手动更新View代码。

#### 3. MVVM：用观察者模式解耦V和P（3根连线）
MVVM进一步削弱了View和ViewModel之间的耦合。它引入了**数据绑定**和**观察者模式**，让View自动响应ViewModel的数据变化。

此时的连线关系变成了：
View → ViewModel(Store) ←→ Model

View仍持有ViewModel的引用，但是ViewModel不在持有view，它做完工作后，只会更新一个可观测的数据状态，完全不知道也不关心
谁在观察这个状态，它完全不知道View的存在。连线数进一步减少到3根，耦合度降到了历史新低。

这就是为什么MVVM能迅速取代MVP成为主流：它用框架自动完成了View和ViewModel之间的同步，省去了大量的模板代码。

#### 4. MVI：统一状态管理，实现单向数据流（2根连线）
MVI 是最新的架构趋势，它在 MVVM 的基础上更进一步，解决了 MVVM 中数据流混乱、状态分散的问题。
MVI 的核心思想是把所有的用户操作都汇聚成 Intent，所有的 UI 状态都汇聚成一个唯一的、不可变的 State，实现严格的单向数据流。
在 MVI 中：
用户操作产生 Intent
View 将 Intent 发送给 ViewModel
ViewModel 处理 Intent，与 Model 交互获取数据
ViewModel 产生一个全新的、不可变的 State
View 观察 State 并重新渲染整个 UI
从引用关系来看，MVI 和 MVVM 一样都是 3 根连线：
View → ViewModel(Store) ←→ Model

ViewModel 仍然完全不持有 View 的任何引用，这一点和 MVVM 是一致的。
但 MVI 的革命性在于它彻底改变了数据流的性质：
MVVM 的数据流是双向的，View 可以直接修改 ViewModel 的数据
MVI 的数据流是严格单向的，所有的状态变化都必须经过 ViewModel 处理
这带来了巨大的优势：
你可以鸟瞰整个页面的所有状态变化
所有的状态都是不可变的，不会出现意外的修改
整个应用的行为是完全可预测、可调试的
可以轻松实现日志、埋点、时间旅行调试等高级功能
代码的复用性和可测试性得到了进一步提升

### 二、架构的局限性：它无法阻止你写出垃圾代码
然而，所有这些架构都有一个共同的局限性：**它们只能提供结构上的约束，无法保证代码质量**。

我见过太多项目：
- 用着最先进的MVVM架构，却写出了5000行的ViewModel
- 严格遵循Clean Architecture，却在Domain层写满了业务耦合的代码
- 采用MVI单向数据流，但是一个复杂页面定义了200+intent，intent名称又臭又长，阅读起来实属灾难

垃圾程序员产生的垃圾代码，并未因采用了先进的架构而消失。
当业务逻辑复杂性提升后，4000+行的Class仍然比比皆是。

我们只是把垃圾从一个房间搬到了另一个房间，并没有真正解决问题。

### 三、比架构更重要的：编程思想
这就引出了我整个系列的核心观点：**架构不是最重要的，架构以外，是编程思想**。

架构只是一种组织代码的方式，它是"术"；而编程思想才是"道"。无论你用什么架构，只要你掌握了正确的编程思想，你就能写出干净、可维护、可扩展的代码。

反过来，如果你没有掌握正确的编程思想，那么无论多么先进的架构，都会被你用成垃圾。

在接下来的文章中，我会分享一种我称之为"Lego架构"的思想。它不是现有主流架构的替代品，而是辅助品。无论你采用MVVM还是MVI或未来的某种新兴架构，Lego架构都可以很好地带来帮助。
